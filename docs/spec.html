Election Night Pipeline Spec

v0.4 2026-10-21 Air date: 2026-11-03 (confirmed) Feed: AP Elections API

1. Scope and assumptions

An 8-hour live broadcast on election night, oriented around independent and third-party candidates in federal races (Senate and House) with national context (balance of power, notable calls). The middleware sits between the AP Elections API and four outputs:

  • Ticker: a dynamic lower third of curated results, delivered to the Ross Carbonite as a keyable layer.
  • Full-screen graphics: race results, balance of power, an independents board, state views. Also delivered to the Carbonite.
  • Studio wall: a browser on the in-studio screen showing whatever the producer selects; the anchor talks to it.
  • Control panel: status, ticker curation, wall/graphic selection. Web-served, access-restricted.
  • Race browser (tier 2): all races and their numbers, separately deployable.

Confirmed: election day is 3 Nov 2026; an AP Elections API key is held, and its entitlements cover all Senate and House races at state and county level (verified Oct 21, section 4). Still to confirm: the studio has a wired internet connection and a machine that can be placed on its LAN.

This document describes the architecture and plan and is updated as decisions are made. The open questions in section 9 list the current unknowns.

3. Architecture

Stack

  • Node 24+ running TypeScript directly (no build step) with the built-in node:sqlite, so there are no native dependencies and nothing to compile on either machine. Fastify for REST, @fastify/websocket for push. One process.
  • Graphics and panel: plain HTML/JS modules sharing one feed client (public/g/feed.js). Svelte and D3 are available if a graphic needs them; the demo uses only d3-geo (with Census geometry) for the county and national maps. The server hosts all fonts and assets; graphics pages make no third-party requests.
  • Process management: pm2 (same commands on macOS, Linux or Windows: pm2 start, pm2 logs, pm2 restart, pm2 startup for boot). Caddy as a plain binary in front where TLS or an auth gate is needed.
  • Deploy is a script that runs git pull && npm ci && pm2 restart ap-ind. It is the only way either machine changes.

Why not containers or serverless

Containers were considered and rejected. The system is one process and one file with no native modules; a container adds an image build, a volume for SQLite and one more layer to debug on the night, without benefit.

Serverless was also rejected. The team's usual host is Vercel, whose serverless model does not run long-lived processes, and the middleware core (a poller on a 20 s cadence, a WebSocket server, a growing SQLite file) is one. Vercel hosts what fits: the race browser (tier 2, read-only, public) and these docs. A Vercel-native variant of the middleware is possible (Vercel Cron triggers each poll at a 1-minute minimum, state in a hosted DB such as Neon or Turso, graphics poll REST every 10–15 s instead of a socket). It is slower, adds two vendors to the critical path and is a second architecture to maintain. It is held in reserve as the cloud fallback if rehearsal shows the studio machine cannot be trusted.

4. Data pipeline

AP Elections API

The feed is a REST API keyed by election date (version v3.2, verified Oct 21). One request returns races with candidates and reporting units; AP returns a nextrequest URL that yields only what changed since, which keeps polling cheap. The key is sent as an x-api-key header, so request URLs, including the stored nextrequest cursor, contain no secret.

GET https://api.ap.org/v3/elections/2026-11-03
    ?officeID=S,H            Senate + House
    &level=state             state-level reporting units (county = P1)
    &resultsType=l           l = live, t = AP test data
    &format=json
    x-api-key: …             header, from server env only
    Accept-Encoding: gzip    required; AP returns 406 without it
→ { apiVersion, timestamp, nextrequest: "…",
    races: [ { raceID, officeID, seatName, seatNum, raceCallStatus, flippedSeat, rankedChoice,
      reportingUnits: [ { statePostal, reportingunitLevel (0 national, 1 state), precinctsReportingPct, eevp, lastUpdated,
        candidates: [ { candidateID, first, last, party, voteCount, incumbent, winner: "X", winnerDateTime,
                        rankedChoiceVoting: [ { eliminated, votes } ] } ] } ] } ] }

Poller loop: fetch, store raw response (gzip, keyed by timestamp), normalize, write snapshot, compute diff against the previous snapshot, emit events, broadcast diff. Cadence 20 s by default, configurable live. On 429 or 5xx: exponential backoff, keep serving last-good, flag status amber. A race seen for the first time is recorded as a baseline and emits no events, so a cold start mid-evening does not announce every call already made.

Verified against the live key (Oct 21). The test feed returns 470 races (435 House, 35 Senate, 51 states) and 30+ non-major party codes (Ind, NPA, Lib, Grn, Una, NP…). County level is included (level=ru, with county FIPS codes); request it per state, since a national county-level pull times out at AP's gateway. Past elections are included: 2020, 2022 and 2024 at the same detail, which covers every "versus last time" comparison without an outside dataset. Ranked-choice races (AK, ME) expose first-round totals plus per-candidate RCV rounds. Candidate last can carry suffixes such as "(write-in)". No photos, bios or polls; these are built separately (see the candidate index). AP exposes no rate-limit headers; the quota is unconfirmed with the account rep.

The test feed was reset on Oct 21 from a finished election to zero votes, apparently ahead of a scheduled simulated count. The delta poller did not see the reset: AP's nextrequest cursor returns only units updated after the last fetch, and the reset data carried older timestamps. Delta polling cannot see a backwards correction. Build-phase fix: a full (non-delta) refresh every few minutes, reconciled against the snapshot, with deltas in between for speed.

The reports feed

GET /v3/reports lists reference tables and roll-ups published beside the results; each has a contentLink under /v3/reports/<id>. Verified readable with the key (Oct 22):

  • Trend (Senate, House, House by state; 2012–2026): AP's balance-of-power tables: Won, Leading, Holdovers, Winning Trend, Current and net change by party, with independents in their own rows by caucus. Balance-of-power graphics read this table; the project's own tally is a cross-check only.
  • Candidates (Senate and House, 2020/2024/2026): every filed candidate with PolID, party, ballot status (on the general ballot, lost primary, withdrew), incumbency and a HasPhoto flag. Used to reconcile the candidate index and the ticker roster.
  • PollHours: closing times by state and congressional district, local, Eastern and UTC. Source for the poll-closing strip; covers split-time-zone states.
  • AdvVotes and VoteTypeAvailability: per-state absentee and early-voting rules, when mail ballots are processed and counted, cure deadlines, and which vote types AP reports separately by reporting unit. Source for the "how this state counts" graphics and for annotating margin movement.
  • elninfo StateVoteCountTiming (2024): per state, when results first arrived, when 50% and 90% were reached, when counting stopped for the night, and the share uncounted on election night. Source for "when to expect results".
  • parties: the full party-code dictionary. Graphics print names from this table, not codes.
  • Also present: Calendar (state deadlines and milestones), EstimatedVotePercentage per race. Not readable with this key: precinct-level caucus reports (405). AP's candidate photos are a separate product; HasPhoto indicates one exists.

Section F of the graphics data options shows these as graphics; each card there lists its endpoints under "Data notes".

Map geometry by reporting unit

AP reports 43 states by county, the six New England states by town or city, and Alaska by State House District. One TopoJSON file per state (scripts/build-geo.mjs, served at /geo/<ST>.json by both apps) matches each state's unit type: counties from the Census county file keyed by FIPS, towns from Census county subdivisions keyed by name, Alaska districts from Census state-legislative boundaries keyed by name. County-level graphics (B4, B6, B8, B10 and the Watch Party race pages) read these files, so every state gets a map that corresponds to the units AP actually reports.

What AP does not supply

Candidate photos and biographies, polling, historical membership of Congress, and AP VoteCast (a separate product). The config/candidates.json index covers the featured races: bios compiled from public sources and keyed by AP candidateID, with photos in public/photos/<id>.jpg restricted to public-domain or Creative Commons images, each visually verified against a second source before inclusion. Campaign-owned photos are referenced by URL and flagged as needing permission; they are not in the repository. The graphics data options page audits every proposed graphic by data source.

Internal model

Race      { id, state, office (S|H), seat, district, callStatus, calledAt,
            precinctsPct, expectedVotePct, lastUpdated, candidates[] }
Candidate { id, name, party, votes, pct, incumbent, winner,
            featured: bool  // independent / third-party of interest, from the curated list }
Event     { id, ts, type (CALL | LEAD_CHANGE | FIRST_RESULTS | THRESHOLD | FEATURED_MOVE | MANUAL),
            raceId, text, priority, expiresAt }

Featured candidates come from a maintained curated list (AP party codes Ind, Una, Lib, Grn, plus any named candidate). Independents are the subject of the broadcast, so they have their own event type and colour across all graphics.

Client protocol

On connect a client receives the full snapshot plus producer state, then diffs. If the socket drops it polls /api/snapshot every 5 s until it reconnects. Every page shows a freshness badge driven by lastSuccessfulPoll: green under 60 s, amber under 3 min, red beyond.

5. Outputs

Each graphic is one URL, 1920×1080, fully self-contained, with query parameters for configuration, e.g. /g/ticker, /g/race?id=…, /g/bop?chamber=senate, /g/independents, /g/state?st=ME, /wall. Background is transparent by default; ?bg=green or ?bg=black for chroma or luma keying.

Ticker

  • Horizontal crawl at a fixed pixel rate, framerate-independent (requestAnimationFrame with delta time), in the lower-third safe area.
  • Queue built server-side: pinned races in producer order, with event items spliced in at the next item boundary. Items carry a priority; a race call interrupts the cycle once, then settles into rotation.
  • Manual items typed in the control panel appear at the next boundary and expire after N loops.
  • Never blank: with no data it shows a holding message; with stale data it keeps crawling the last-good numbers and shows the staleness badge.
  • Race item format: ME-SEN · King (I) 52.1% · Doe (R) 41.3% · 38% in; call format: AP CALL · NE-SEN · Osborn (I) defeats ….

Full-screen graphics

  • Race result: horizontal bars per candidate, votes and share, precincts/expected vote reporting, AP call flag. Independents coloured distinctly.
  • Balance of power: Senate and House seat bars with called, leading and not-yet-reporting segments, independents as their own segment.
  • Independents board: every featured candidate in one table, sorted by share or margin; the signature graphic for this broadcast.
  • State overview: all federal races in one state.
  • Graphics animate in and update in place; numbers tween so a live update on air does not jump.

Studio wall

The /wall page shows one of the full-screen graphics or a composite (balance of power plus the independents board), chosen in the control panel. Larger type and a solid background. Same data socket.

Control panel

  • Status strip: AP connection, last poll time, poll interval, error count, server identity (studio or cloud), connected clients.
  • Ticker: search races, pin, reorder, remove; compose manual items; preview of the current queue.
  • Wall and graphics: pick the wall view; stage a full-screen graphic (choose race, chamber, state) and copy its URL for the graphics operator.
  • Event log with mute per event type.

6. Getting graphics into the Carbonite

The Carbonite takes SDI (and on some models HDMI) video inputs and has no browser, so the pages must be rendered to video. Options, in order of preference:

OptPathNotes
AGraphics PC running CasparCG Server with a Blackmagic DeckLink (e.g. Duo 2). CasparCG renders the HTML pages and outputs fill and key on two SDI outputs; Carbonite does a linear key.True alpha, standard broadcast workflow, free software. Needs the PC and card (~$500–1000) and one SDI pair per layer.
BGraphics PC, Chromium full-screen on a second display, HDMI→SDI converter, Carbonite chroma or luma key over a green or black page background.Cheapest, works with any PC. Edges on anti-aliased text are worse than linear key; fine for a ticker, acceptable for full-screens.
CRoss XPression (if the facility has it) reading the server's JSON via DataLinq, with the templates built in XPression.Native to the production team's workflow, but graphics are then built twice (web for the wall, XPression for air).
DNDI with alpha (OBS browser source → NDI → NDI/SDI converter supporting fill+key, or native NDI input if the Carbonite has it).Depends on the specific Carbonite model and converters on hand.
Recommendation: A, with B as a fallback that can be set up in an afternoon. Both let the production team treat each graphic as a plain video source. Full-screens and the ticker each get their own output so they can be layered independently.

7. Reliability and security

Reliability

  • Primary on a machine on the studio LAN, so the graphics PC and wall keep being served even if studio internet drops (an outage then only stops new data). Identical code on a small VPS polling AP independently as the mirror. Graphics pages resolve the server through one hostname that can be repointed; the control panel shows which one is live.
  • AP or internet outage: last-good data served, staleness badge on every page, alert in the panel. Nothing on air goes blank.
  • Every raw AP response is kept. Replay mode feeds a recording back through the poller at 1× or faster for rehearsal and post-mortems.
  • Process supervised by pm2 (restart on crash, start on boot, log rotation); state is in SQLite so a restart resumes within one poll from the persisted nextrequest cursor.
  • Graphics pages render from a plain /api/snapshot fetch first, then attach the socket; if the socket drops they poll every 5 s until it returns.
  • Health endpoint and a simple watchdog that pages the engineer on duty.

Security

  • AP key lives only in server environment, loaded from a gitignored .env (template in .env.example); browsers never call AP and the key never appears in logs or the repo.
  • Control panel: username/password login with session cookie, CSRF protection, request rate limiting, audit log of producer actions.
  • Default posture: not reachable from the public internet. Studio access over LAN; remote producers over Tailscale (or Cloudflare Access). If public exposure is required, Caddy enforces TLS, auth and rate limits at the edge.
  • Graphics and wall pages are read-only; when served remotely they require a signed token in the URL so they cannot be enumerated.
  • Race browser (tier 2) can be public; it is read-only, cached, and hosted on Vercel alongside these docs.

9. Open questions

  1. AP quota and test dates. Entitlements are confirmed (all Senate and House races, state and county level, past elections). Still needed from the account rep: the polling interval the contract allows, the dates of AP's scheduled live tests, and whether VoteCast is wanted and licensable.
  2. Which independents. Who is on the curated list? Should "independent" mean AP party codes outside Dem/GOP, a maintained named list, or both? Are major-party candidates in races with a strong independent also featured?
  3. Carbonite details. Which model (Black, Ultra, Mosaic, other), how many free inputs, SDI or HDMI, 1080i59.94 or 1080p? Does the facility already own XPression, a DeckLink, CasparCG, or NDI converters? Who is the graphics operator on the night?
  4. Studio wall. Resolution and aspect, what currently drives it, and whether it is on the same LAN as the Carbonite.
  5. Network. Is studio internet wired and reliable? Is there a backup (LTE)? Can a mini-PC be placed there and administered remotely?
  6. Operators. How many producers use the control panel, from where (studio, remote), and on what devices?
  7. Design. Is there a brand or style guide, fonts, and party colours, and who owns graphic design? A clean default set can be shipped.
  8. Outside data. Prior-year results and the seats-not-up baseline come from AP. Still to build and verify: polling for the featured races, candidate bios and photo rights (index started), quotes, and the history of independents in Congress. Who owns editorial verification of these?
  9. Public demo hosting. The live server cannot run on Vercel (long-lived process, WebSockets, SQLite). A shareable copy of the demo needs a small persistent host (Railway, Render, Fly or a VPS) behind a password. Vercel keeps the docs only, or is retired once the server also serves them.
  10. Hardware budget. Can a DeckLink and a mini-PC be bought this week if option A is chosen?
  11. Air window. Exact on-air hours and time zone, and whether anything else (anchor tablet, social clips) should draw from the same feed.
